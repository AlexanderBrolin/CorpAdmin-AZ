# Agent Iface Address Reconcile — приведение живого интерфейса к managed-конфигу

**Beads epic:** CorpAdmin-AZ-c9w
**Beads root bug:** CorpAdmin-AZ-3f9 (P0, хотфикс применён вручную)
**Beads (сознательно вне объёма):** CorpAdmin-AZ-84e (P2, `apply_path` не поднимает iface
при совпадении sha) · CorpAdmin-AZ-mqp (P2, `_apply_wg_config` не вызывает hook) ·
CorpAdmin-AZ-3up (P3, MTU из CP не доезжает до ноды)
**Date:** 2026-09-02
**Author:** brolin (with Claude)

## Problem

2026-09-02 обнаружено, что нода `wgfi4` двое суток обслуживала клиентов наполовину:
из 805 пиров на интерфейсах `antizapret` и `vpn` **551 (68%) был маршрутно недостижим**.

Живое состояние интерфейса разошлось с конфигом на диске:

| | конфиг `/etc/wireguard/antizapret.conf` | живой интерфейс |
|---|---|---|
| wgfi4 | `Address = 10.29.8.1/21` | `10.29.8.1/24` |
| wgfi3 | `Address = 10.29.8.1/21` | `10.29.8.1/21` |

`/24` покрывает только `10.29.8.0–10.29.8.255`. Клиенты с адресами `10.29.9.x` (256 шт.),
`10.29.10.x` (256) и `10.29.11.x` (36) не имели connected-маршрута, и обратный трафик уходил
в шлюз хостера:

```
ip route get 10.29.9.5   -> 10.29.9.5 via 78.17.39.1 dev eth0    # в интернет, не в туннель
ip route get 10.29.8.94  -> 10.29.8.94 dev antizapret            # рабочий диапазон
```

Handshake при этом проходил — ответ уходит клиенту на его endpoint по UDP через `eth0`
и маршрута в туннель не требует. Клиент показывал «подключено», трафик не шёл.
Симптом подтверждён на клиенте `natalya_aglicheva-1` (`10.29.11.35`).

Побочный эффект: балансировщик на CP делит новые потоки ровно 50/50 (счётчики DNAT
7720 против 7845), но клиент, попавший на wgfi4 и не получивший связи, переподключается —
и рано или поздно закрепляется на wgfi3. Храповик дал устойчивый перекос 101 против 44
активных пиров. В прошлой сессии этот перекос ошибочно списали на «тяжёлых качальщиков».

### Почему конфиг и интерфейс разошлись — три дефекта

**Дефект 1 — `_apply_wg_config()` не вызывает никакой hook.**
[corpweb_sync_agent.py:764](../../../agent/corpweb_sync_agent.py#L764) при регистрации
получает от CP `wg_config` и патчит `Address`/`ListenPort`/`MTU` в конфигах через `re.sub`,
[записывает файл](../../../agent/corpweb_sync_agent.py#L842) — и на этом останавливается.
Интерфейс не трогается вообще.

**Дефект 2 — `apply_path()` пропускает hook при совпадении sha.**
[corpweb_sync_agent.py:635](../../../agent/corpweb_sync_agent.py#L635): если файл на диске
уже совпадает с эталоном, функция возвращает `False` и hook не выполняется. Это отдельная
открытая задача **84e**; здесь важно, что она закрывает второй путь к применению адреса.

**Дефект 3 (корневой) — `wg syncconf` конструктивно не умеет применять `Address`.**
[corpweb_sync_agent.py:614](../../../agent/corpweb_sync_agent.py#L614): когда интерфейс уже
поднят, `apply_iface_conf()` выполняет

```
wg syncconf <iface> <(wg-quick strip <iface>)
```

`wg-quick strip` вырезает из конфига `Address`, `MTU`, `DNS`, `Table` и `PreUp`/`PostUp` —
всё, что относится к wg-quick, а не к самому wg. Проверено на wgfi4, а не принято на веру:

| `[Interface]` в конфиге на диске | после `wg-quick strip antizapret` |
|---|---|
| `PrivateKey = …` | `PrivateKey = …` |
| **`Address = 10.29.8.1/21`** | **строки нет** |
| `ListenPort = 51443` | `ListenPort = 51443` |

**Адрес живого интерфейса не применяется никогда.** Тот же замер попутно доказывает, что
`ListenPort` до `wg syncconf` доходит, то есть смена порта из CP работает.

Единственный путь, которым правильный адрес мог попасть на интерфейс, — поднятие с нуля
через `wg-quick up`, читающее полный конфиг. На wgfi3 так исторически и вышло. На wgfi4
интерфейсы подняты при провижининге из шаблона установщика AntiZapret
`/etc/wireguard/templates/antizapret.conf`, где `Address = 10.29.8.1/24`, и с тех пор
ни разу не переподнимались.

Проверено на ноде, что рендер конфига из шаблона выполняется **только один раз**:
`client.sh` делает его в `initWireGuard()` под охраной `if [[ ! -f /etc/wireguard/key ]]`,
то есть пока не сгенерированы серверные ключи. `doall.sh` `client.sh` не вызывает вовсе.
Значит после провижининга единственный писатель этого конфига — агент, и шаблон с `/24`
больше никогда не участвует. Это важно для дизайна: конфигу на диске можно доверять
как источнику желаемого состояния (см. инвариант в разделе «Точки вызова»).

Следствие шире одного инцидента: **любое изменение `Address` или `MTU`, пришедшее из CP,
молча не доезжает ни до одной ноды.** Шаблон с `/24` лежит на обеих нодах и станет миной
для каждой следующей.

### Почему мониторинг молчал

`/etc/wireguard/antizapret.conf` входит в `MANAGED_FILES`, и его sha на диске **совпадал**
с эталоном CP. Панель показывала `drift = 0 из 14` и ноду «Онлайн». Существующий контроль
сверяет содержимое файлов и не знает ничего о том, соответствует ли этому содержимому
работающая система.

## Goals

1. Живой адрес интерфейса приводится к значению из managed-конфига автоматически,
   без ручного вмешательства.
2. Приведение не рвёт существующие клиентские соединения: без `wg-quick down/up`,
   без рестарта юнита, интерфейс ни на мгновение не остаётся без адреса.
3. Расхождение живого состояния с конфигом видно в метриках на каждом heartbeat —
   независимо от того, было оно исправлено или нет.
4. Ошибка в новом коде не может уронить агента и не может зациклиться на прод-интерфейсе.
5. Радиус поражения ограничен: общий путь применения файлов (`apply_path`,
   `apply_iface_conf`) не меняется.

## Non-goals (явный scope-out)

- **Правка `apply_path()` / `apply_iface_conf()`.** Дефекты 1 и 2 перестают влиять на адрес,
  как только сверщик работает независимо от хуков. Трогать общий путь всех 14 managed-файлов
  ради этой задачи — неоправданный риск. Задача 84e остаётся отдельной.
- **Любая работа с MTU — ни правки, ни детекта.** Изначально в дизайне был детект
  расхождения MTU. Аудит показал, что он **не может сработать**: ни один из четырёх
  конфигов ни на wgfi3, ни на wgfi4 не содержит строки `MTU`, поэтому желаемое значение
  всегда неизвестно и проверка всегда пропускается. Причина — отдельный дефект:
  CP шлёт `wg_config = {"mtu": 1420}`, а `_apply_wg_config()` применяет его через
  `re.sub(r'^MTU\s*=\s*.*$', …)`, который умеет только заменить существующую строку,
  но не добавить её. Цепочка CP → конфиг → ядро мертва целиком; сейчас безвредно, потому
  что живой MTU и так равен 1420. Заведено отдельной задачей **CorpAdmin-AZ-3up**.
  Писать код, который не может сработать ни на одной существующей ноде, здесь не будем.
- **Отображение в панели.** Метрики пишутся в `nodes.metrics`; вывод в UI — задача того же
  класса, что открытая **t2r** (escape-drift по нодам), и делается вместе с ней.
- **Управление маршрутами.** Connected-маршрут следует за адресом автоматически; сегодняшняя
  проверка подтвердила, что правки адреса достаточно для восстановления трафика.
- **Исправление шаблона `/etc/wireguard/templates/*.conf` на нодах.** Шаблон принадлежит
  upstream-установщику AntiZapret и агентом не управляется. Сверщик делает его безвредным.
- **Поднятие упавшего интерфейса.** Это зона `apply_iface_conf`; сверщик работает только
  с уже поднятыми интерфейсами.

### Полнота: все параметры интерфейса, которыми управляет CP

Чтобы ничего не осталось молча недоделанным, перечень закрыт целиком:

| параметр | доезжает ли до ядра сегодня | что делаем |
|---|---|---|
| `Address` | **нет** — вырезается `wg-quick strip` | чинит сверщик (эта задача) |
| `ListenPort` | да — переживает strip, применяется `wg syncconf` (проверено) | ничего не требуется |
| `MTU` | **нет** — не попадает даже в конфиг | вне объёма, **CorpAdmin-AZ-3up** |

Других параметров `_apply_wg_config()` не трогает.

## Design

### Компоненты

Всё добавляется в [`agent/corpweb_sync_agent.py`](../../../agent/corpweb_sync_agent.py)
рядом с существующими функциями работы с интерфейсами.

`_IFACE_CONFS` размещается в блоке констант рядом с `MANAGED_FILES` (начало файла) — раньше
и `_apply_wg_config()`, и `_IFACES`, оба из которых на неё ссылаются. Функции сверщика —
рядом с `_iface_is_up()` / `apply_iface_conf()`, в том же тематическом блоке.

```python
_IFACE_CONFS: dict[str, str]                        # iface → conf path
_ADDR_RECONCILE_MAX_FAILURES = 3

def _ip_addr_show(iface) -> subprocess.CompletedProcess | None   # ip -j -4 addr show dev <iface>
def _iface_is_up(iface) -> bool                                  # существующая, переписана поверх _ip_addr_show
def _iface_state(iface) -> list[str] | None                      # адреса, либо None если интерфейса нет
def _conf_addresses(conf_path) -> list[str]                      # из строки Address =
def _ip_addr(op, addr, iface) -> bool                            # ip addr add|del
def reconcile_iface_addresses(apply: bool) -> dict               # → метрики
```

### Переиспользование существующего кода

Проверено grep'ом по репозиторию перед добавлением:

1. **`_IFACE_CONFS` не дублируется, и убирает уже существующее дублирование.**
   Маппинг iface → путь конфига сейчас захардкожен внутри
   [`_apply_wg_config()`](../../../agent/corpweb_sync_agent.py#L778) как локальный `iface_map`.
   Выносится в module-level константу, `_apply_wg_config()` начинает читать её же.

   Кроме того, список тех же четырёх интерфейсов **уже существует** отдельно —
   [`_IFACES`](../../../agent/corpweb_sync_agent.py#L890), используемый в `collect_metrics()`
   и `collect_peers()`. Добавить третий список было бы прямым нарушением: `_IFACES`
   переопределяется как `tuple(_IFACE_CONFS)`. Порядок сохраняется (dict в Python 3.7+
   упорядочен по вставке), комментарий про «первые два — базовые, последние два — escape»
   остаётся верным, а источник правды становится один.

   Заодно упрощается сам `_apply_wg_config()`: ключи в `wg_config` от CP единообразны
   (`antizapret_address`/`antizapret_listen_port`, `az_escape_address`/`az_escape_listen_port`
   и т.д.), поэтому вместо четырёх повторяющихся литеральных блоков функция итерируется
   по `_IFACE_CONFS` и берёт `cfg.get(f"{iface}_address")` / `cfg.get(f"{iface}_listen_port")`.
   Поведение не меняется.
2. **`_iface_is_up()` не дублируется.** Существующая функция
   ([:573](../../../agent/corpweb_sync_agent.py#L573)) выполняет `ip link show <iface>` и
   проверяет returncode. Новому коду нужен тот же факт плюс сами адреса. Обе функции
   строятся поверх одного вызова `_ip_addr_show()`:
   - `_iface_is_up()` смотрит **только на returncode** — контракт сохраняется в точности;
   - `_iface_state()` дополнительно разбирает JSON.

   Ключевое для безопасности: сбой разбора JSON (старый iproute2 без `-j`) даёт
   `_iface_state() → None`, но **не** влияет на `_iface_is_up()`. Иначе `apply_iface_conf()`
   счёл бы поднятый интерфейс упавшим и выполнил бы `systemctl start` на работающем.
3. **`parse_setup_env()` проверен и отклонён.** В файле есть готовый парсер
   ([:208](../../../agent/corpweb_sync_agent.py#L208)) для `/root/antizapret/setup`.
   Для wg-конфига он не годится, и причина конкретная: это парсер плоского `KEY=VALUE`
   без секций, складывающий результат в `dict`. Повторяющиеся ключи схлопываются —
   при двух строках `Address` вторая была бы потеряна, а сверщик удалил бы соответствующий
   адрес с живого интерфейса. Своя функция разбора необходима.
4. **Обработка ошибок и логирование** повторяют существующий паттерн `subprocess.run(...)`
   + `try/except CalledProcessError` + `log.error` — так написаны все 8 вызовов в файле.
   Общий враппер не вводится: его нет сейчас, и создавать новую абстракцию ради трёх
   вызовов противоречит конвенции файла.
5. **Метрики** расширяют существующий паттерн `escape_drift_detected` /
   `escape_drift_applied_count` из [`sync_escape_rules()`](../../../agent/corpweb_sync_agent.py#L314),
   включая module-level счётчик и слияние словарей в `send_heartbeat()`.
   Новых механизмов доставки метрик не появляется.

### Чтение живого состояния

Один вызов `ip -j -4 addr show dev <iface>`:

```json
[{"ifname":"antizapret","mtu":1420,
  "addr_info":[{"family":"inet","local":"10.29.8.1","prefixlen":21,"scope":"global"}]}]
```

Читается только `addr_info`; поле `mtu` игнорируется (см. Non-goals).

`-j` (JSON) вместо разбора текста — устойчиво к смене формата вывода и является штатным
режимом iproute2. Проверено на обеих прод-нодах: `iproute2-6.15.0` на wgfi3 (Debian 12)
и wgfi4 (Debian 13).

Учитываются только адреса `family == "inet"` и `scope == "global"`; нормализуются в вид
`<ip>/<prefixlen>`.

Проверено экспериментально, что коды возврата и вывод различают три состояния — это и есть
основание разделить `_iface_is_up()` и `_iface_state()`:

| состояние интерфейса | rc | stdout |
|---|---|---|
| есть, с IPv4 | 0 | `[{"ifname":…,"mtu":…,"addr_info":[…]}]` |
| **есть, без IPv4** | **0** | **`[]`** |
| отсутствует | 1 | пусто |

Средняя строка — причина, по которой `_iface_is_up()` не может опираться на разбор JSON:
поднятый интерфейс без IPv4-адреса даёт пустой массив, и наивная проверка «JSON непустой»
объявила бы его упавшим. Поэтому:

- `_iface_is_up()` → `rc == 0`;
- `_iface_state()` → `None` при `rc != 0` (интерфейса нет) и при непарсящемся выводе;
  при `rc == 0` и `[]` → `[]` — интерфейс есть, адресов нет.

Пустой список — рабочий случай, а не ошибочный: `want - live` даст полный набор желаемых
адресов, они будут добавлены, удалять будет нечего. Отличать его от `None` обязательно:
`None` означает «интерфейса нет, не трогаем», `[]` — «интерфейс есть, адресов нет, добавляем».

### Чтение желаемого состояния

`Address` из конфига. Формат wg-quick допускает список через запятую и несколько строк
`Address`. Разбор:

- собираются все строки `^Address\s*=`;
- значение делится по запятой, пробелы отбрасываются;
- каждый элемент валидируется через `ipaddress.ip_interface` (stdlib, без новых зависимостей);
- IPv6 отбрасывается — сверщик работает только с IPv4, как и `ip -4 addr show`;
- результат нормализуется в `<ip>/<prefixlen>` тем же представлением, что и живое состояние,
  чтобы сравнение было посимвольным.

Если конфиг отсутствует, нечитаем, или после разбора не осталось ни одного валидного
IPv4-адреса — **интерфейс пропускается целиком**. Мы никогда не трогаем интерфейс, не зная
достоверно желаемого состояния.

Поддержка списка через запятую и нескольких строк `Address` — не «на всякий случай», а
требование корректности. Сверщик удаляет всё, чего нет в `want`. Если конфиг содержит
`Address = 10.29.8.1/21, 10.29.16.1/24`, а разбор возьмёт только первый элемент, второй
адрес окажется в `live - want` и будет **удалён с живого интерфейса**. Неполный разбор здесь
означает не «меньше функциональности», а активную порчу конфигурации.

### Алгоритм приведения (на один интерфейс)

Предусловия: интерфейс есть в `_IFACE_CONFS`, конфиг существует и даёт непустой `want`,
`_iface_state(iface)` вернул не `None`. Иначе — пропуск без единой команды.

Признак «интерфейс существует» здесь — именно `_iface_state(iface) is not None`;
`_iface_is_up()` сверщик не вызывает. Эта функция остаётся исключительно для
`apply_iface_conf()`, и общий у них только нижележащий `_ip_addr_show()`.

1. `live = set(_iface_state(iface))`, `want = set(_conf_addresses(conf))`.
2. `live == want` → расхождения нет, счётчик неудач этого интерфейса сбрасывается, выход.
   Сброс здесь намеренный: расхождение, исчезнувшее само (например, поправили руками),
   снимает интерфейс с backoff.
3. Расхождение зафиксировано в метриках. Выход без правки, если `apply=False`
   **или** интерфейс уже исчерпал backoff (см. ниже) — во втором случае в метрике
   поднимается `iface_addr_drift_failed`.
4. Перед любой мутацией — отказ работать с пустым `want`. Предусловие это уже гарантирует,
   но функция, которая выполняет удаления, не должна на него полагаться: снять все адреса
   с живого интерфейса — единственный исход, которого здесь быть не может никогда.
5. **Сначала добавление**: для каждого `a in want - live` выполняется `ip addr add a dev iface`.
   Интерфейс ни на мгновение не остаётся без адреса.
6. Если хотя бы одно добавление не удалось — удаления **не начинаются**, интерфейс помечается
   как неуспешный, выход.
7. **Затем удаление**: для каждого `a in live - want` выполняется `ip addr del a dev iface`.
   После каждого удаления живое состояние перечитывается:
   - если какой-то адрес из `want` исчез (случай `promote_secondaries=0`, когда удаление
     primary сносит secondary в той же подсети) — адрес немедленно добавляется обратно,
     дальнейшие удаления на этом интерфейсе прекращаются, интерфейс помечается как неуспешный;
   - если после удаления на интерфейсе не осталось ни одного адреса — то же самое;
   - **если живое состояние вообще не читается** (`_iface_state` вернул `None`) — вслепую
     переприменяются **все** адреса из `want`, после чего удаления прекращаются, интерфейс
     помечается как неуспешный.

   Последний пункт добавлен по итогам ревью Task 4 и расходится с первоначальным текстом плана,
   который в этом случае просто выходил. Причина: `None` возникает по пяти разным поводам, и
   в четырёх из них (нет `ip`, ненулевой код возврата, непарсящийся JSON, не-список в ответе)
   интерфейс жив и мог только что потерять нужный адрес. Выход без восстановления — единственный
   путь, на котором сверщик оставлял бы интерфейс с недостачей. `want` здесь достоверен: он из
   конфига, нечитаемо только живое состояние. Повторное добавление существующего адреса падает
   с EEXIST — шумно в логе, но безвредно.
8. Финальная проверка: `live == want`. Если да — счётчик успешных правок увеличивается,
   счётчик неудач интерфейса сбрасывается. Если нет — счётчик неудач увеличивается.

Порядок «добавить, потом удалить» — не теоретическое соображение: ровно так выполнялся
ручной хотфикс 2026-09-02, и он подтвердил, что `ip addr change` в этом ядре **не заменяет**
адрес, а добавляет второй. Сверщик обязан работать множествами, а не «менять префикс».

### Backoff

`startup_reconcile()` вызывается [не единожды](../../../agent/corpweb_sync_agent.py#L1144),
а внутри `while True` перед каждым `stream_events()` — то есть при каждом переподключении SSE,
которое при недоступном CP происходит каждые 5 секунд.

Module-level `dict[str, int]` считает подряд идущие неудачи на интерфейс. По достижении
`_ADDR_RECONCILE_MAX_FAILURES = 3` приведение для этого интерфейса прекращается до конца
жизни процесса; детект и репорт продолжаются, в метрике поднимается `iface_addr_drift_failed`.
Успешное приведение сбрасывает счётчик.

Это защита от бесконечного цикла правок на прод-интерфейсе, если правка почему-то
не закрепляется.

### Точки вызова

| где | режим | обоснование |
|---|---|---|
| `startup_reconcile()`, сразу после цикла применения файлов и **до** push'а seed-блобов | `apply=True` | конфиги на диске к этому моменту уже актуальны |
| `send_heartbeat()` | `apply=False` | видимость каждые 30 с без права что-либо менять |

**Инвариант, на котором держится доверие к конфигу.** Сверщик берёт желаемое состояние из
файла на диске, а не из ответа CP напрямую. Это корректно только потому, что вызов стоит
**после** цикла `apply_path()` в том же `startup_reconcile()`: к этому моменту конфиг уже
перезаписан версией CP. Порядок в функции менять нельзя — если сверщик окажется раньше
цикла, он будет приводить интерфейс к устаревшему локальному файлу.

Второе основание — проверенный факт из раздела Problem: после провижининга шаблон
установщика в этот конфиг больше не пишет, других писателей нет.

Вызов в `send_heartbeat()` оборачивается в `try/except` и сливается в `metrics` тем же
способом, что и `sync_escape_rules()` — с тем же поведением при неожиданном исключении.

**Осознанное отступление от конвенции файла.** `sync_escape_rules()`, вызываемый из
`send_heartbeat()`, не только детектит, но и **применяет** изменения (переписывает
`custom-up.sh` при расхождении). То есть в этом файле уже есть прецедент «heartbeat чинит».
Сверщик адресов сознательно так **не** делает: скрипт-хук и живой сетевой интерфейс
прод-ноды — разной цены ошибки, а heartbeat идёт каждые 30 секунд. Правка остаётся
в `startup_reconcile()`, где она редка и предсказуема. Отступление зафиксировано здесь,
чтобы при чтении кода оно не выглядело недосмотром.

### Метрики

Именование повторяет существующую пару `escape_drift_detected` /
`escape_drift_applied_count` из `sync_escape_rules()` — тот же префикс-подлежащее,
тот же суффикс `_detected` / `_applied_count`:

```
iface_addr_drift_detected: bool              # есть хотя бы одно расхождение
iface_addr_drift: {                          # только расходящиеся интерфейсы
    "antizapret": {"live": ["10.29.8.1/24"], "want": ["10.29.8.1/21"]}
}
iface_addr_drift_applied_count: int          # успешных приведений за жизнь процесса
iface_addr_drift_failed: bool                # backoff исчерпан ИЛИ обработка интерфейса упала
iface_addr_error: str | dict                 # см. ниже — два разных случая под одним ключом
```

**`iface_addr_drift_failed` выставляется в обоих режимах** — и при `apply=True`, и при
`apply=False`. Это уточнение внесено по итогам ревью Task 5: проверка насыщения изначально
стояла *после* выхода по `apply`, из-за чего флаг мог возникнуть только на apply-проходе —
а его результат `startup_reconcile()` отбрасывает, и до CP доезжают только метрики heartbeat'а.
Метрика, существующая ради «здесь нужен человек», не доходила бы до человека никогда.
Строка `log.error` при этом осталась только на apply-проходах: detect-only идёт раз в 30 секунд
и не должен засорять журнал.

**`iface_addr_drift_failed` — это на самом деле два разных условия под одним флагом**, и
`ADD-NODE.md` до правки по итогам финального ревью советовал на этот флаг одну и ту же
реакцию — `systemctl restart corpweb-sync-agent` — которая осмысленна только для первого:
1. интерфейс исчерпал backoff (три подряд неудачных попытки приведения) — рестарт агента
   сбрасывает счётчик и даёт ещё три попытки;
2. обработка интерфейса внутри `reconcile_iface_addresses()` бросила исключение (перехватывается
   тем же defensive `except Exception`, что не даёт упасть heartbeat'у) — рестарт тут ничего не
   чинит, если код продолжает бросать то же самое.

`iface_addr_error` теперь различает эти два случая — но заполняется в двух разных местах и в
разной форме:
- в `send_heartbeat()`, как и раньше, зеркало существующего `escape_error` из
  `sync_escape_rules()`: **строка**, если вопреки docstring'у сверщика вызов
  `reconcile_iface_addresses()` целиком выбросил исключение;
- внутри самого `reconcile_iface_addresses()` — **словарь** `{имя_интерфейса: описание
  исключения}` для каждого интерфейса, чья обработка упала в per-iface `except`. Раз здесь
  цикл продолжает работать после ошибки на одном интерфейсе, ошибок может быть несколько —
  отсюда карта, а не одна строка.

Оператор различает случай (1) от случая (2) по наличию и форме `iface_addr_error`: пусто —
чистое исчерпание backoff, рестарт агента уместен; словарь с именем интерфейса — код упал,
рестарт не поможет, если причина не в самом сервисе, нужно смотреть `journalctl` и трассировку
в логе (`log.error("Address reconcile failed for %s: %s", ...)`) и чинить причину.

`iface_addr_drift` отражает состояние **на момент проверки**: если проход нашёл расхождение
и тут же его исправил, ключ в этом проходе присутствует, а факт починки виден по
`iface_addr_drift_applied_count`. Следующий heartbeat расхождения уже не покажет.

Ключи с пустым значением не отправляются, чтобы не раздувать `nodes.metrics` в БД —
как и в `sync_escape_rules()`.

### Обработка ошибок

Сверщик не выпускает исключений наружу ни при каких условиях: отсутствие `ip` в PATH,
непарсящийся JSON, недоступный конфиг, ненулевой код возврата `ip addr` — всё уходит в
`log.error` и в метрику. Агент не должен падать из-за диагностики.

## Риски и что их снимает

| риск | что снимает |
|---|---|
| Ошибка сверщика оставит интерфейс без адреса | Добавление строго раньше удаления; удаление прекращается, если пропал нужный адрес; последний адрес не удаляется |
| `promote_secondaries=0` на будущей ноде снесёт secondary при удалении primary | Перечитывание живого состояния после каждого удаления и немедленный откат |
| Цикл правок при частых реконнектах SSE | Идемпотентность (правка только при реальном расхождении) + backoff на 3 неудачи |
| Регрессия в общем пути применения файлов | `apply_path()` и `apply_iface_conf()` не изменяются |
| Старый iproute2 без `-j` на будущей ноде | `_iface_is_up()` опирается на returncode, а не на JSON; сверщик при непарсящемся выводе пропускает интерфейс |
| Сверщик испортит интерфейс, который не должен трогать | Работает только по `_IFACE_CONFS`; при пустом или невалидном `want` — пропуск |

## Тестирование

**Новый файл `agent/tests/test_iface_addr_reconcile.py`.** В `agent/tests/` действует
конвенция «одна фича — свой файл»: `test_escape_rules.py`, `test_seed_blob.py`, при том что
`test_sync_agent.py` остаётся за общим ядром агента. Дописывать сверщик в общий файл
означало бы нарушить сложившееся разделение.

Стиль повторяет существующие файлы точно:

- pytest-классы `class TestXxx:` **без** наследования от `unittest.TestCase`
  (в репозитории не используется ни одного `TestCase`);
- `from unittest.mock import patch`, `sys.path.insert(...)` и
  `import corpweb_sync_agent as agent  # noqa: E402` — как в `test_escape_rules.py`
  и `test_seed_blob.py`;
- **обязательная autouse-фикстура сброса module-level состояния** (счётчики неудач и
  применённых правок) между тестами — по образцу `reset_timers` в `test_sync_agent.py`.
  Без неё тест на backoff отравит соседние;
- ассерты на **полный argv**, а не на подстроку — по образцу проверок `wg` против `awg`
  в текущих тестах интерфейсов.

Разбор входных данных:
1. `_conf_addresses` — обычная строка, лишние пробелы, список через запятую,
   несколько строк `Address`, IPv6 отбрасывается, отсутствие `Address` → пустой список,
   мусорное значение → пустой список.
2. `_iface_state` — разбор реального JSON `ip -j -4 addr show`; интерфейса нет (rc 1) → `None`;
   непарсящийся вывод → `None`; **rc 0 и `[]` → `[]`** (пустой список, не `None`);
   адреса не-`inet` и не-`global` отфильтровываются.
3. `_iface_is_up` сохраняет контракт: returncode 0 → `True`, ненулевой → `False`,
   непарсящийся JSON при rc 0 → по-прежнему `True`, **пустой массив `[]` при rc 0 →
   по-прежнему `True`** (регрессия на поднятый интерфейс без IPv4).

Поведение сверщика:
4. `live == want` → **ни одной** мутирующей команды.
5. Регрессия инцидента: live `10.29.8.1/24`, conf `Address = 10.29.8.1/21` →
   ровно `ip addr add 10.29.8.1/21 dev antizapret`, затем `ip addr del 10.29.8.1/24 dev antizapret`,
   в этом порядке.
6. `apply=False` при расхождении → мутирующих команд нет, метрика заполнена.
7. Сбой `ip addr add` → удаления не выполняются.
8. Сценарий `promote_secondaries=0`: после `del` нужный адрес пропал → повторный `add`,
   дальнейшие `del` не выполняются, интерфейс помечен неуспешным.
9. Backoff: после трёх неудачных проходов четвёртый не вызывает `ip addr` вовсе.
10. Успех после неудачи сбрасывает счётчик.
11. Интерфейс не поднят → пропуск без команд.
12. `want` пуст / конфига нет → пропуск без команд.
13. Интерфейс поднят, но адресов нет (`live` пуст, `want` непуст) → выполняются только
    `ip addr add`, ни одного `ip addr del`.
14. Исключение внутри сверщика не ломает `send_heartbeat()`.

Существующие наборы (`agent` 112, `backend` 354) должны остаться зелёными.

Рефакторинги делаются не вслепую — их прикрывают уже написанные тесты:
`TestApplyWgConfigEscapeIfaces` (три теста, все четыре интерфейса, включая случай
отсутствующего конфига) защищает переход `_apply_wg_config()` на `_IFACE_CONFS`;
`test_collect_metrics_includes_four_active_peer_keys` и
`test_collect_peers_enumerates_all_four_ifaces` защищают вывод `_IFACES` из той же
константы. Если рефакторинг сломает состав интерфейсов, эти тесты покраснеют.

## Проверка на проде после выката

Хотфикс уже привёл wgfi4 в порядок, поэтому «до/после» на живом расхождении не воспроизвести
безопасно. План проверки:

1. Обе ноды: в `nodes.metrics` **отсутствуют** ключи `iface_addr_drift_detected`,
   `iface_addr_drift` и `iface_addr_drift_failed`. Именно отсутствуют, а не равны `false` —
   ключи с пустым значением агент не отправляет, поэтому проверять нужно
   `metrics ? 'iface_addr_drift'`, а не сравнение со значением.
2. Контролируемая проверка на wgfi4 в непиковое время: временно добавить лишний адрес
   `ip addr add 10.29.99.1/32 dev antizapret`, дождаться heartbeat → расхождение видно
   в метриках; рестарт агента → адрес снят, `iface_addr_drift_applied_count = 1`, клиенты не разорваны.
3. Сравнить число активных пиров до и после проверки — просадки быть не должно.
