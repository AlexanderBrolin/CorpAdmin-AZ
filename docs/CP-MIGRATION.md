# Перенос Control Plane на новый сервер

Эпик: **CorpAdmin-AZ-4gz**. Инвентаризация снята с прода 2026-08-31 07:00–07:15 UTC.

**Причина переноса.** Между текущим CP `92.118.85.140` и обеими нодами теряется 80–100% TCP
в обе стороны, при 0% потерь ICMP и полностью исправном UDP. Замер: нода шлёт SYN, CP отвечает
SYN-ACK за 15 мкс, SYN-ACK до ноды не доходит, нода ретрансмитит. Firewall'ы обеих машин
проверены и ни при чём. Из-за этого агенты не держат SSE-поток, heartbeat'ы приходят раз в
2–18 минут вместо 30 секунд, конфиги доезжают через раз. Новый сервер — у того же хостера,
что и ноды, в РФ-сегменте.

### Трафик — главный параметр при выборе тарифа

Замер 2026-08-31 07:14 UTC (утро, низкая нагрузка): **RX 2170 КБ/с, TX 2172 КБ/с, 4026 пакетов/с**.
Накопленный с загрузки объём: **24 ГБ RX + 24 ГБ TX за 1 ч 27 мин** — это ~4.6 МБ/с в каждую
сторону в среднем. В пересчёте: **≈380 ГБ/сутки в каждую сторону, ≈12 ТБ/мес исходящего,
до ~24 ТБ/мес если хостер считает обе стороны.** Днём в рабочее время будет выше.

Весь клиентский VPN-трафик проходит через CP дважды (клиент→CP→нода и обратно), поэтому
**нужен тариф с безлимитным или очень большим трафиком и каналом от 1 Гбит/с.**
CPU и память не критичны: нагрузка 0.02, память 500 МБ из 3.9 ГБ, форвардинг идёт в ядре.

### iptables

**filter** — минимальный: политики ACCEPT, drop `ctstate INVALID` в INPUT/FORWARD/OUTPUT,
rate-limit на новые SSH-подключения по порту 22.

**nat** — это и есть балансировщик, 16 правил DNAT + 2 SNAT:

- DNAT для UDP-портов `51443, 51080, 52443, 52080, 540, 580, 500, 53443` — по два правила на
  порт (первое с `--probability`, второе fallback).
- SNAT `-d <IP ноды> -j SNAT --to-source 92.118.85.140` — по одному на ноду.

На момент снятия у ноды `89.125.39.44` вероятность `0.00000000000` (выведена из балансировки),
весь трафик идёт на `89.125.198.77`. Порты 500/53443 присутствуют — они восстановились сами
при перезагрузке CP 2026-08-31 05:37 через `ensure_ports_reconciled()`.

Сохранение: `/etc/iptables/rules.v4`, `netfilter-persistent` enabled.
**Правила пересоздаются приложением, переносить их файлом не нужно** — достаточно поднять
бэкенд с правильным `cp_ip` и нажать «Сохранить» в балансировщике.

> ⚠️ **Ловушка при первом старте на чистом сервере.** `ensure_ports_reconciled()`
> ([balancer.py](../corpweb/backend/app/services/balancer.py)) при старте бэкенда видит пустой
> nat-table, не находит текущих весов и подставляет **всем** нодам `weight=50, enabled=True`:
> ```python
> live = current.get(str(n.private_ip))
> "weight":  live["weight"]  if live else 50,
> "enabled": live["enabled"] if live else True,
> ```
> То есть на новом CP при первом же запуске **wgfi2-ssh автоматически получит 50% трафика**,
> хотя сейчас она сознательно выведена из балансировки и держит список пиров от 28 августа.
> Это мгновенно воспроизведёт исходную аварию. Порядок действий на этапе 2 составлен так,
> чтобы этого не случилось.

## 3. Что жёстко привязано к IP — критический список

Смены DNS **недостаточно**. Проверено на обеих нодах:

1. **`/etc/hosts` на обеих нодах** содержит `92.118.85.140  wgfi2.p4i.ru`.
   Пока эта строка не изменена, агенты будут ходить на старый IP независимо от DNS.
   Это самый частый способ провалить такой перенос.
2. **`system_settings.cp_ip`** в БД = `92.118.85.140`. Используется как источник SNAT
   (`_detect_cp_ip` в `corpweb/backend/app/api/v1/balancer.py`). Если не поменять — SNAT будет
   переписывать источник в старый IP и ответы нод уйдут в никуда.
3. **`/root/antizapret/config/allow-ips.txt` на обеих нодах** содержит `92.118.85.140`.
   Сейчас не задействован (`ATTACK_PROTECTION=n`), но если защиту когда-нибудь включат —
   новый CP будет забанен как сканер. Файл управляется из панели через `wg_file_state`,
   правится централизованно.
4. **DNS `wgfi2.p4i.ru` A-запись** → новый IP. TTL снизить заранее.

Привязок по имени, которые менять **не надо** (имя сохраняется):
`CONTROL_PLANE_URL=https://wgfi2.p4i.ru` в `/etc/corpweb-sync-agent.env` на нодах,
`OPENVPN_HOST` / `WIREGUARD_HOST` в `/root/antizapret/setup`, `Endpoint = wgfi2.p4i.ru:<порт>`
в клиентских конфигах, `FRONTEND_URL` / `BACKEND_URL` / `CORS_ORIGINS` / `LB_ENDPOINT_HOST`.

**Токены агентов (`AGENT_TOKEN`) лежат в таблице `nodes` и переносятся вместе с БД** —
перевыпускать и перерегистрировать ноды не нужно.

**Клиентские конфиги перевыпускать не нужно** — в них указано имя, а не IP.

## 4. Порядок переноса

### Этап 0 — подготовка, без простоя

1. Снизить TTL A-записи `wgfi2.p4i.ru` до 300 секунд минимум за сутки до переноса.
2. Получить доступ на новый сервер, проверить требования из раздела 2.
3. **Проверить связность новый CP ↔ ноды по TCP** — 20 попыток на 443 и 2201 в обе стороны.
   Если теряется хоть что-то, дальше не идти: перенос не решит задачу.
4. Снять свежий `pg_dump` и положить в надёжное место (не в session-scratchpad).

### Этап 1 — развернуть новый сервер, старый продолжает работать

1. Debian 12, `apt` до актуального, часовой пояс UTC, chrony.
2. Пакеты: `nginx postgresql-15 python3.11 python3.11-venv certbot python3-certbot-nginx iptables-persistent conntrack`.
   `conntrack` нужен для сброса залипших соединений при смене весов — см. **CorpAdmin-AZ-zwj**.
3. sysctl из раздела 1, обязательно `ip_forward=1`.
4. sshd на 2201, ключи `brolin`, sudo NOPASSWD. **Отключить `PasswordAuthentication`** — на
   старом сервере он включён, это лишний риск, переносить не стоит.
5. Скопировать `/opt/corpweb/{backend,frontend,agent}`. `venv` **не копировать**, пересобрать
   на месте: `python3.11 -m venv venv && venv/bin/pip install -r requirements.txt`
   (`requirements.txt` есть, 46 строк; в текущем venv 59 пакетов с учётом зависимостей —
   для точного совпадения снять `pip freeze` со старого сервера и сверить).
   `app.bak-406fz` и `frontend.bak-406fz` не переносить.
6. Скопировать `/etc/letsencrypt` целиком — сертификат заработает сразу, до переключения DNS.
7. Скопировать `/etc/nginx/nginx.conf`, проверить `nginx -t`.
8. Развернуть БД: `createdb` + роль `corpweb` + восстановление дампа. Проверить `alembic head = 0007`.
9. Скопировать `.env`, поменять в нём только пароль БД, если он меняется.
10. Поднять `corpweb-backend`, проверить локально: `curl -s localhost:8000/api/v1/auth/config`.
11. **Не открывать наружу и не переключать DNS.** Проверка через `curl --resolve`.

### Этап 2 — переключение

Простой клиентов — от единиц секунд до пары минут на переподключение тоннелей.

1. В БД нового CP: `UPDATE system_settings SET cp_ip = '<новый IP>' WHERE id = 1;`
2. **Сразу после первого старта бэкенда** проверить `iptables -t nat -S` на новом CP.
   Из-за ловушки с `ensure_ports_reconciled` там будет 50/50 на обе ноды. Если wgfi2-ssh
   ещё не синхронизирована — открыть балансировщик и выставить ей 0%, **до** переключения DNS.
3. На **обеих нодах** заменить строку в `/etc/hosts` на новый IP. Без этого агенты не переедут.
4. Переключить A-запись `wgfi2.p4i.ru` на новый IP.
5. Открыть страницу балансировщика и нажать «Сохранить» — это пересоздаст DNAT/SNAT
   с новым `cp_ip`. Проверить `iptables -t nat -S`: должны быть 16 DNAT и 2 SNAT с новым адресом
   и нужными весами.
6. Дождаться регистрации агентов: в логе бэкенда `POST /api/v1/agent/register` от обоих IP,
   затем регулярные heartbeat'ы. `last_seen` обеих нод должен стать секундами.
7. Обновить `allow-ips.txt` через панель: заменить старый IP на новый.
8. На старом CP остановить `corpweb-backend` и `nginx`, чтобы исключить работу двух CP разом.

### Этап 3 — проверка

1. Обе ноды: `last_seen` < 60 с, `synced` = да по всем путям.
2. `certbot renew --dry-run` на новом сервере.
3. Реальное число активных пиров прямо с ноды:
   `wg show antizapret latest-handshakes | awk -v n=$(date +%s) '$2>0 && n-$2<180' | wc -l`.
4. Замер доли клиентов, получающих ответ (tcpdump на CP по порту 52443).
5. Панель: вход, список конфигов, скачивание конфига, создание тестового конфига и проверка,
   что он доезжает до обеих нод.
6. Через сутки — проверить, что фильтрации TCP нет: 20 попыток TCP в обе стороны.

### Этап 4 — возврат wgfi2-ssh в балансировку

**Только после того, как её агент синхронизировался** (`last_seen` секунды, `synced` = да).
Иначе повторится авария: на ноде останется список доступа от 28 августа.

После установки веса — **обязательно** сбросить залипшие соединения на CP:

```
conntrack -D -p udp --orig-dst <новый IP CP>
```

Без этого существующие клиенты останутся на прежней ноде: AmneziaWG шлёт junk 20 пакетов/с,
запись conntrack не истекает никогда. Автоматизация этого — задача **CorpAdmin-AZ-zwj**.

## 5. Откат

Старый сервер не выключать минимум 3 суток.

1. Вернуть A-запись `wgfi2.p4i.ru` на `92.118.85.140`.
2. Вернуть `92.118.85.140 wgfi2.p4i.ru` в `/etc/hosts` на обеих нодах.
3. На старом CP: `UPDATE system_settings SET cp_ip='92.118.85.140'`, запустить `corpweb-backend`
   и `nginx`, нажать «Сохранить» в балансировщике.
4. Если за время работы нового CP менялись конфиги — перелить БД обратно.

Точка невозврата — шаг 4 отката: расхождение баз. Поэтому в первые сутки после переноса
лучше не создавать и не удалять конфиги.

## 6. Риски

| Риск | Митигация |
|---|---|
| Забыли `/etc/hosts` на нодах | вынесено в раздел 3 отдельным пунктом, проверять до переключения DNS |
| Забыли `cp_ip` в БД | SNAT уйдёт на старый адрес; проверять `iptables -t nat -S` после «Сохранить» |
| Клиенты держат старый IP в кеше | TTL снижен заранее; переподключение тоннеля решает |
| Два CP работают одновременно | остановить бэкенд и nginx на старом сразу после переключения |
| На новом сервере та же фильтрация | проверяется на этапе 0 **до** любых изменений |
| Возврат wgfi2-ssh с устаревшим списком пиров | этап 4, только после подтверждённой синхронизации |
| Потеря клиентов при смене весов | `conntrack -D` вручную, до реализации CorpAdmin-AZ-zwj |

## 7. Смежные задачи

- **CorpAdmin-AZ-zwj** (P1) — балансировщик должен сам сбрасывать conntrack при смене весов.
- **CorpAdmin-AZ-2p1** (P1) — панель врёт: мёртвая нода «Онлайн», мониторинг показывает ноль
  при живых клиентах, ошибки API рисуются как «нет подключений».
- **CorpAdmin-AZ-ar7** (P1) — heartbeat агента отправляется только внутри цикла чтения SSE;
  нет SSE — нет ни одного heartbeat'а. Плюс отсутствует read-таймаут.
- **CorpAdmin-AZ-4t8** (P3) — `connection_logs` не пишутся, 30 МБ bloat, истории нет.
- **CorpAdmin-AZ-jh5** (P1) — на новом сервере не воспроизводить `PasswordAuthentication yes`
  и разобраться с утёкшим root-паролём.
